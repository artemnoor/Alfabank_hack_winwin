# Policy v2.1 — замороженный offline-кандидатный маршрут

**Версия:** `2.1.0-spike`  
**Состояние:** frozen for experimental T09 handoff; не production policy.  
**Источник данных:** только сохранённые ответы Jev от 2026-10-14; новых Jev/Polza запросов не было.

## Правила

1. Если сохранённый ответ технически валиден, сохранить Choice topic и confidence, распределение Choice и все 15 оценок Noul.
2. Для каждого события независимо: `score <= 0.20` → `negative`; `0.20 < score < 0.80` → `abstain`; `score >= 0.80` → положительный **кандидат**. Границы включительны.
3. Если положительных кандидатов нет, сохранить результат без event candidates. Это не технический отказ и не false negative для отсутствующего ответа.
4. Если кандидаты есть и `insufficient_evidence_score >= 0.80`, удержать эти кандидаты для проверки; известные candidates не передаются дальше.
5. `unlisted_event_score >= 0.80` создаёт отдельную задачу проверки неизвестного события и не блокирует известные кандидаты.
6. Низкий Choice confidence и отдельные `abstain` не блокируют другие категории и сами по себе не создают review task.
7. Отсутствующий результат Jev остаётся `missing`; ему нельзя создавать вымышленные scores, пустой классификационный ответ или false negative.

## Наблюдаемый результат на зафиксированном наборе

- 45 сохранённых ответов из 49 непустых исходных новостей; 4 отсутствующих исключены.
- 32 новости с кандидатами; 40 кандидатных меток.
- 0 evidence-hold и 0 unlisted review задач на исходных настройках.
- Против предварительных меток: 34 TP, 6 FP, 7 FN; precision 0.850, recall 0.829, F1 0.840; точный набор 34/45.
- Это арифметика по предварительной однопользовательской разметке синтетики, не оценка production-качества. Ноль review не является сигналом безопасности.

## Граница доказательств

Кандидат — только подсказка для следующего анализа, не подтверждённый факт. Jev output не содержит точных source evidence spans. T09 обязан получить разрешённый исходный текст и самостоятельно извлечь/проверить утверждение и evidence. Нельзя применять score Jev как подтверждение, создавать confirmed event из одной метки или обходить owner/policy проверку.

В taxonomy v0.3.0 `insufficient_evidence` объединяет сомнение в основной теме и в наличии бизнес-события. Поэтому этот сигнал может консервативно удержать event candidate из-за topic-only сомнения. Policy v2.1 не умеет различить эти причины; сохранённый сигнал не переинтерпретируется задним числом. Proposal taxonomy v0.4.2 разделяет смысл для будущего эксперимента, но не применялась к сохранённым ответам и не тестировалась live.

## Связь с утверждённым контрактом

Это описание не добавляет DTO, полей, endpoint или generated contract. На границе T09 можно рассматривать только **выпущенные** коды кандидатов как `event_hints` для последующего extraction; удержанные коды не выпускать как hints. Список scores, thresholds, held candidates, unlisted task, missing-result state, policy/taxonomy version и provenance необходимо сохранять во внутреннем versioned trace/record, если утверждённая операция это допускает. Не добавлять их в OpenAPI без решения владельца контракта.

Значение topic передавать только в форме, совместимой с текущим `ClassificationOutput`; использовать предусмотренное контрактом значение raw score/method/calibration и не объявлять оценку откалиброванной. Точный enum `score_method` должен браться из сгенерированного контракта, а не выдумываться по этому документу.

## Воспроизводимость

Точные SHA-256 кода Python и браузерной реализации, входных источников и сохранённого результата записаны в `POLICY_V2.1.manifest.json`. Песочница пересчитывает только локально; применение новых ползунков — counterfactual-переинтерпретация старых scores, не новый запрос и не новый запуск Jev.
