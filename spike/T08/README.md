# T08 spike: классификация новостей через Jev

**Статус:** изолированный эксперимент; в production не подключён. Папка содержит прототип и результаты тестирования, предназначенные для последующего рассмотрения и возможной интеграции в основной код после завершения live-проверки, независимой приёмки и согласования таксономии. Автоматического переноса или merge в `main` нет.

## Что проверяется

Единственный классификатор этого эксперимента — **Jev**. Список категорий и определения заданы проектом, а не генерируются моделью. Черновик `taxonomy.json` содержит 10 именованных общих тем и вариант `other_uncertain` (всего 11 вариантов Choice), а также 15 бизнес-событий.

Для одной главной темы используется Jev `Choice`. Для каждого из 15 бизнес-событий задаётся отдельный независимый Jev `Noul`; поэтому одна новость может иметь несколько меток событий. Ещё один `Noul` проверяет подтверждённое коммерческое или операционное событие вне списка; макроэкономическая мера без прямо описанного делового события не считается таким событием. Отдельный `Noul` выявляет расплывчатые, неполные, спекулятивные, противоречивые или неподтверждённые сведения и направляет их на review. Итого запрос содержит один `Choice` и 17 независимых `Noul` вопросов. Если тема или событие неясны, результат направляется в `uncertain`/`other`, без создания новых категорий. Пустой ввод отсекается локально.

В версии таксономии `0.3.0-spike` уточнена граница `legal_enforcement`: метка требует отдельного юридического развития сверх основного события. Обычное открытие процедуры банкротства остаётся только `insolvency_default`; отдельное заявление кредитора после дефолта даёт обе метки; подтверждение исполнения санкционного решения остаётся `sanctions`.

`corpus.json` содержит **49 вымышленных русскоязычных новостей и один пустой ввод** (50 тест-кейсов). Метки написаны вручную и используются только для оценки: они не добавляются в запросы Jev. Каждая из 15 категорий событий имеет не менее двух положительных примеров. В наборе есть одиночные события, сочетания событий, неопределённые сообщения, отрицания, неподтверждённые слухи, пример с инструкцией внутри новости, событие вне списка и текст без бизнес-события. Набор полностью синтетический и не содержит реальных публикаций или пользовательских данных. Он включает явное макроэкономическое отрицание для unlisted-сигнала, событие вне списка, неоднозначную неполную заметку и дополнительный экологический пример без бизнес-события.

Для отдельного исследования добавлен корпус [`experiments/deep-v1/`](experiments/deep-v1/): 160 синтетических строк (A — 76 основных, B — 36 границ категорий, C — 24 metamorphic stimuli, D — 24 контрольных). Его версия и SHA закреплены в `manifest.json`; исходные `corpus.json`, `taxonomy.json` и прежние результаты не менялись. Gold labels написал один аннотатор: для оценки качества нужна слепая независимая разметка и adjudication. Кейс B24 помечен как неразрешённая неоднозначность и исключается из оценки до adjudication. D физически отделён и не используется для tuning, но его метки видны в репозитории и автор корпуса их видел, поэтому это **не слепой контрольный набор**. Текущий live-runner намеренно принимает только закреплённые исходные 49 текстов; новые 160 кейсов структурно проверены, но Jev на них не запускался.

Тексты таксономии и корпуса закреплены SHA-256 в harness. Live-клиент откажется работать, если их байты изменены. Он принимает только заранее выведенные хеши точных запросов из проверенного корпуса, запрашивает модель Polza `typesafe/jev`, устанавливает `provider.allow_fallbacks=false` в request и проверяет точную версию Jev в ответе. Фактическое соблюдение флага Polza не проверено. Повтор одного request hash блокируется только внутри одного запуска процесса; кумулятивный лимит между запусками не хранится.

## Границы эксперимента

- Код находится только в `spike/T08/`. Он не регистрирует production implementation и не меняет API, CLI, Playground, OpenAPI, fixture registry или зависимости приложения.
- IPTC, GDELT/CAMEO, Event Registry и RavenPack использованы только как ориентиры при составлении собственного списка. Они не классифицируют новости и не поставляют модели.
- Live-режим может отправить только закреплённые синтетические новости. Реальные статьи, unknown/manual материалы и произвольный текст не принимаются.
- Для native `Choice`/`Noul` используется System One Jev через официальный Polza AI API: `POST https://polza.ai/api/v1/systemone`, Bearer key из `POLZA_AI_API_KEY`, model ID `typesafe/jev`. Транспорт фиксирован на HTTPS endpoint, без редиректов и повторов; ограничены время запроса и размер ответа.
- В отчёт попадают ID синтетического случая, оценки/метки Jev, версия модели, token usage, `usage.cost_rub` и локальное время запроса. Текст, запрос, полный ответ провайдера, ключ и исходный текст ошибок не записываются.
- Для event/unlisted Noul оценки `≤ 0.2` считаются отрицательными, `≥ 0.8` — положительными; промежуточные требуют review. Для Noul-сигнала недостаточности данных любое значение выше `0.2` направляется на review. Choice ниже `0.5` также требует review. Все пороги экспериментальные, не оптимизированы и не откалиброваны для новостей; это не production policy.

## Состояние живого доступа

На 2026-10-14 выполнен один live-запрос по закреплённой синтетической новости `e01-supply-rail` через правильный Polza API и модель `typesafe/jev`. Получен валидный ответ Jev `jev-1.13.0`: тема `industry_trade_supply`, положительный `supply_chain_disruption` (0.90), score события вне списка 0.53; из-за этого результат направлен harness в `uncertain`. Стоимость по `usage.cost_rub` — 0.10391619 ₽, вход/выход — 5905/492 токена, latency — 844 мс. Сохранён санитарно обработанный артефакт [`results/jev-live-pilot-20261014T094655Z.json`](results/jev-live-pilot-20261014T094655Z.json). Smoke запускался предыдущей версией client/runner (`5ef1c6c…` / `3a4ed49…`); текущий request hash совпадает с сохранённым, но текущая ревизия не отправляла повторный live-запрос. Это один smoke-case, не оценка качества и не полный benchmark.

Исторические HTTP 451 относятся к прежним запросам на прямой TypeSafe host (`api.typesafe.ai`), а не к использованному проектом Polza endpoint. Они не устанавливают причину отказа и ничего не говорят о доступности Polza. В ходе исправления один дополнительный запрос случайно ушёл на прежний TypeSafe host из регрессионного теста с legacy env key; результат сохранён только как `sanitized_request_error` в [`results/jev-live-pilot-20261014T094544Z.json`](results/jev-live-pilot-20261014T094544Z.json). Ответ, тело ошибки и ключ не сохранены. Регрессионный тест исправлен: теперь пустой `POLZA_AI_API_KEY` останавливает запуск до сети даже при наличии legacy `TYPESAFE_API_KEY`.

Один исторический Polza round-trip подтверждает базовую совместимость использованного request/response path. Качество модели на русском остаётся **NOT MEASURED**: один случай недостаточен, а его draft gold labels не проходили независимую adjudication. Запрос устанавливал `provider.allow_fallbacks=false`, но фактическое соблюдение этой настройки и выбранный upstream provider не подтверждены. Остальные live-запросы не отправлялись; они могут тарифицироваться. Для следующей партии нужен отдельный бюджет/разрешение. Прямой TypeSafe endpoint больше не используется; сетевые ограничения не обходятся.

## Запуск

Из корня репозитория:

```powershell
python spike/T08/run_spike.py
python -m unittest discover -s spike/T08 -p "test*.py" -v
```

Офлайн-проверки валидируют исходный корпус и таксономию, расширенные split hashes и gold labels A/B/C, метаморфические пары, форму Choice/Noul, strict response validation, пороги, метрики, транспортные ошибки, allowlist, отсутствие повторов, redirect/proxy и скрытие деталей. D проверяется только по manifest hash и числу строк, не передаётся evaluator. Тестовый модуль блокирует стандартные Python socket entrypoints на время offline suite; это process-level guard, а не гарантия OS/container-level egress isolation. Все transport cases используют локальные подмены; единственный live-запрос описан выше.

По официальной документации Polza System One использует `POST https://polza.ai/api/v1/systemone`, Bearer key, `state`, `model`, `questions` и optional `provider`. Jev-specific page указывает model ID `typesafe/jev`; ответ содержит фактическую версию (`jev-1.13.0`), `answers` и `usage` с `input_tokens`, `output_tokens`, `cost_rub`. `Choice` допускает до 255 вариантов, System One — 1–256 вопросов; код использует более строгий spike-local предел 20 как budget guard. Документация описывает `confidence` как поле ответа, но не задаёт проверяемую формулу; код проверяет только тип/диапазон и вероятности. Исторический запрос `Choice`/`Noul` и usage-схема прошли один фактический HTTP round-trip; текущий request hash с ним совпадает, но текущий клиент заново не проверялся live. Источники: [Polza System One API](https://polza.ai/docs/api-reference/systemone/create), [Polza Jev guide](https://polza.ai/jev), [Polza Jev model ID](https://polza.ai/models/typesafe/jev).

Подробный свежий отчёт аудита находится в [`TEST_REPORT.md`](TEST_REPORT.md), машинная копия — [`TEST_REPORT.json`](TEST_REPORT.json), офлайн-проверка таксономии — [`experiments/deep-v1/TAXONOMY_REVIEW.md`](experiments/deep-v1/TAXONOMY_REVIEW.md).

Live-запуск по умолчанию делает не более одного запроса. После отдельного подтверждения бюджета сначала можно выполнить 10 synthetic cases:

```powershell
python spike/T08/run_spike.py --live --max-calls 10
```

Предел `--max-calls` проверяется на один запуск процесса; cumulative budget между повторными запусками не хранится и не ограничивается автоматически. Не повторяй live-команду и не увеличивай лимит без отдельного бюджета. Полный baseline содержит 49 непустых случаев и не запускался.

Ключ Polza должен быть предоставлен в среде Windows под именем `POLZA_AI_API_KEY`; код читает его из окружения, не печатает и не сохраняет. Никаких legacy TypeSafe key fallback нет. Ошибка первого сетевого запроса останавливает прогон, автоматических повторов нет. Из provider error сохраняется только HTTP status, тело и остальные поля ответа отбрасываются. Отчёт с безопасно обработанными ответами сохраняется новым файлом в `spike/T08/results/`. Любые дополнительные платные запросы требуют отдельного согласованного бюджета; один smoke-case не доказывает статистическое качество или production-готовность.

Транспорт отправляет запрос только на официальный HTTPS endpoint, запрещает redirects и явно отключает автоматическое чтение proxy-настроек окружения. Это не используется для обхода ограничений доступа.

## Что решить до возможной интеграции

1. Согласовать состав и границы предложенных категорий.
2. После успешного live-прогона вручную оценить ошибки, распознавание неопределённости и threshold sweep. Не подбирать production thresholds по малой синтетической выборке.
3. Отдельно согласовать преобразование оценок Jev в нормативные `TopicScore`/`event_hints`; этот spike не заявляет соответствие output DTO.
4. Интеграцию в существующий `Understanding.classify`, Dependency Gateway, policy и Run History проводить только как отдельную работу T08 с контрактными, replay и egress-тестами.
5. Не отправлять реальные/unknown/manual данные во внешний API до подтверждения trusted-source policy gate и разрешённого egress.
