# T08 → T09: проектная граница event-кандидатов

Этот документ описывает предполагаемую границу между этапами только как заметку spike. Фактической передачи, интеграции T09, public DTO или production interface нет; реализация T09 не начинается.

## Что отдаёт Policy v2.1

В локальном расчёте Policy v2.1 после проверки формы и допустимых значений сохранённого ответа T08:

1. Сохраняет выбранную тему Choice, её confidence, вероятности Choice и все оценки 15 Noul.
2. Каждая Noul-оценка `>= 0.80` становится event-кандидатом. Она не утверждает, что событие произошло.
3. Если положительных кандидатов нет, T08 сохраняет результат без списка event-кандидатов.
4. Если кандидаты есть и `insufficient_evidence_score >= 0.80`, симуляция удерживает их и показывает задачу проверки.
5. `unlisted_event_score >= 0.80` показывает отдельную задачу поиска/разметки события вне списка. Этот сигнал не блокирует известные event-кандидаты.
6. Низкий Choice score и Noul `abstain` сохраняются как сигналы, но не блокируют кандидатов и сами не создают review в этой экспериментальной policy.

Границы включительные. Noul `negative` — `score <= 0.20`, `positive` — `score >= 0.80`, остальное — `abstain`. Слайдеры песочницы локально меняют интерпретацию уже сохранённых оценок, не запускают Jev.

## Черновая форма записи кандидата

Это полевая карта для будущего обсуждения интерфейса с T09, не контракт:

```json
{
  "source_case_id": "e01-supply-rail",
  "policy_version": "2.1.0-spike",
  "taxonomy_version": "0.3.0-spike",
  "topic": {
    "code": "industry_trade_supply",
    "score": 1.0,
    "state": "saved"
  },
  "event_candidate": {
    "code": "supply_chain_disruption",
    "score": 0.9,
    "state": "positive",
    "assertion_status": "candidate_unconfirmed"
  },
  "routing": {
    "held_for_insufficient_evidence": false,
    "separate_unlisted_review": false
  }
}
```

В реальном интеграционном контексте потребуется защищённая ссылка на исходный документ и scope/policy provenance. Текущий Jev output не содержит evidence spans. T09 должен получать текст через разрешённый Documents API/port и самостоятельно привязывать извлечённое утверждение к точным фрагментам источника; score Jev не заменяет evidence.

## Что можно / нельзя считать готовым

- **Готово для обсуждения:** список event-кодов-кандидатов, scores и независимые маршруты evidence/unlisted, рассчитанные на сохранённых synthetic результатах.
- **Не готово к runtime:** DTO, права доступа, tenant/sandbox scope, storage, HTTP/CLI связи, provenance и перенос документа между владельцами.
- **Не является фактом:** ни один event-кандидат. Следующим слоем требуется подтверждение по тексту и evidence spans.
- **Не тестировалось с новой taxonomy:** latest proposal v0.4.2 не отправлялась в Jev; её новая формулировка evidence-сигнала не сопоставима с сохранёнными score v0.3. Набор из 60 visible-validation текстов и новый пул из 40 кандидатов видимы в репозитории, не размечались и не классифицировались; они не являются blind test. Для будущего слепого набора нужны независимый custodian, две независимые human-разметки и adjudication.

## Фактический результат saved pilot

Policy v2.1 локально сформировала 40 candidate-меток в 32 из 45 историй, показала 0 review-задач на порогах 0.80/0.80 и дала 6 расхождений-FP и 7 расхождений-FN относительно предварительных labels. Это отладочный расчёт на синтетике; фактической передачи в T09 нет, а безопасное снятие проверки не подтверждено этими числами.

## Контрактная граница для будущей передачи

Policy v2.1 заморожена как локальный эксперимент в [`POLICY_V2.1.md`](POLICY_V2.1.md), её входы и реализации закреплены в [`POLICY_V2.1.manifest.json`](POLICY_V2.1.manifest.json). Это не разрешение внедрять policy в runtime.

- Передавать можно только выпущенные коды как подсказки для extraction. Удержанные из-за `insufficient_evidence` коды не превращать в `event_hints`.
- `event_hints` не доказывают событие и не дают права на `confirmed`. T09 самостоятельно читает исходный документ через разрешённый owner interface, извлекает формулировки и строит точные evidence spans.
- Если DTO T09 использует `ClassificationOutput`, topic/event hints должны соответствовать текущему OpenAPI и generated contracts. Не добавлять туда score кандидата, причины удержания, отдельную задачу `unlisted`, policy version или отсутствие live-ответа; внутреннюю трассу сохранять в предусмотренном versioned run/provenance storage. Новые поля требуют отдельного согласования.
- Отсутствие ответа Jev не равно корректному результату с пустыми `event_hints`. В сохранённом наборе четыре исходные новости без ответа; они не создают candidates.
- Для сохранённых ответов использовалась taxonomy v0.3.0. В ней insufficient-evidence question охватывает сомнение и в основной теме, и в событии. Поэтому текущий hold иногда может сработать только из-за сомнения в теме. Не ослаблять этот порог по этим же 45 примерам; сначала решить семантику taxonomy и сделать новый разрешённый пилот.
- Отдельный `unlisted_event` — задача поиска/обсуждения недостающего кода. Он не равен `other_uncertain` и не блокирует уже известные candidates.

## Новые входы для будущей проверки

`experiments/future-blind-candidate-v1/news.json` содержит 40 новых синтетических текстов без labels и model outputs. Они не вошли в нынешние метрики и были созданы без выбора кейсов по текущим Jev errors. Это **candidate pool**, не готовый blind benchmark: входы видимы в репозитории, а независимые human labels ещё не созданы. Условия будущей label-blind оценки и custodian описаны рядом в `ANNOTATION_GUIDE.md`.
