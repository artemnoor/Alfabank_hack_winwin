# Предложение taxonomy v0.4.0-spike

**Статус:** draft / awaiting user review / not evaluated. Это предложение не заменяет и не меняет `taxonomy.json` v0.3.0-spike. Новый live прогон не выполнялся, поэтому улучшение Jev не доказано.

- Исходная taxonomy: `taxonomy.json`, SHA-256 `855a61f9b6c199d8440b8b81bbd09234e376896576121ed163af2ed7f0c1455d`.
- Proposal: `experiments/taxonomy-v0.4-proposal/taxonomy.json`, SHA-256 указан в соседнем `manifest.json`.
- Все topic/event codes и вопросы Choice/Noul сохранены. Изменены только критерии, пояснения и правила аннотации, чтобы следующий опыт сравнивал границы, а не новую систему меток.

## Почему предлагаются правки

|---|---|---|---|
| `sanctions` / `trade_restriction` | Одна формальная мера может быть санкцией и ограничением торговли, но одна метка не должна автоматически выводить другую. e31 — совместный positive; e25 — ложная sanctions-метка на юридическом действии. | Отдельно требовать подтверждение санкционного режима и отдельно ограничение трансграничного потока; обсуждение/угроза не равны введению. | Можно потерять реальный combined event, если описание слишком узкое. ## Темы, которые требуют main-subject tie-break

Предлагается выбирать одну тему по основному предмету статьи, не по actor или случайному слову:

- `business_companies` — остаточная тема о конкретной компании, только если более узкая тема не доминирует.
- `industry_trade_supply` — физическое производство/перевозка/потоки товаров; event labels остаются независимыми.
- `energy_resources` — энергия, топливо, добыча и энергорынки; не считать любую воду/сырьё энергетикой автоматически.
- `law_regulation` — общий нормативный инструмент и юридическое производство нужно различать.
- `other_uncertain` — открытая проблема: известное событие вне списка и недостаточные доказательства не должны схлопываться в одно состояние. Отдельное разделение может потребовать согласования контракта/DTO; proposal не добавляет поле и не утверждает новый wire format.

Эти изменения важны для e06/e07/e09/e10/e12/e14/e18/e24/e28/e29/e33/e42/e45/e47. Gold не менялся. Текущий topic accuracy не может быть честным основанием для изменения labels, пока человек не проверил спорные случаи.

## Позитивные/негативные/граничные примеры для следующей версии

1. Для каждой пары выше создать минимум по два подтверждённых положительных примера на класс, по два контрастных отрицательных и по два lifecycle-boundary примера.
2. Для одного и того же wording менять только факт: «ввели» / «обсуждают» / «отменили»; «остановил» / «может остановить»; «пропустил платеж» / «рассматривает банкротство».
3. Добавить явные multi-label cases с независимыми evidence spans, и похожие single-label cases без второго события.
4. Gold ставят люди до просмотра Jev outputs; AI review используется только как предложение.
5. Сначала утвердить определения и примеры, затем зафиксировать version/hash; не проводить live-тест до отдельного решения по бюджету.

## Предлагаемый сравнимый эксперимент

Сначала adjudicate baseline и заморозить labels. Затем выполнить парный offline prompt build check для v0.3/v0.4 и, при отдельном разрешении бюджета, ограниченный live pilot на заранее выбранных synthetic cases. Не подбирать пороги на blind split. Измерить per-category precision/recall/F1, topic confusion, exact-set, abstain/review rates и ошибки в спорных контрастах. Если Noul scores остаются некалиброванными, не выдавать их за вероятности.

## Решения владельца, необходимые до использования

- Утвердить семантику `other_uncertain` для «known out-of-list» vs «insufficient evidence» без изменения OpenAPI по умолчанию.
- Утвердить, считается ли официально объявленная будущая цена уже событием.
- Определить минимальную материальность для hiring/layoffs как `labor_workforce_event`.
- Утвердить, что legal_enforcement может быть положительным без признания нарушения, если есть официальное действие.
- Решить, допустимы ли `trade_restriction` + `regulation_tax_change` и `sanctions` одновременно при отдельных evidence spans.
