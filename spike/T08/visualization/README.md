# T08 · интерактивная песочница Jev

`index.html` — автономная локальная лаборатория для просмотра уже сохранённых ответов Jev на синтетические новости. Никакой сервер, Docker, PostgreSQL, ключ Polza AI или интернет для открытия файла не нужны.

## Открыть

Откройте `index.html` двойным щелчком в Windows. Страница работает как локальный файл `file://`.

## Что внутри

- Список всех 50 записей корпуса: 49 непустых текстов и один пустой `no_content`.
- 45 настоящих сохранённых ответов Jev из пилота `jev-live-aggregate-20261014-v4.json`.
- Четыре отсутствующих ответа — `e23`, `e35`, `e41`, `e43` — отображаются без выдуманных оценок и не считаются пропущенными событиями.
- Все 11 тем и 15 бизнес-событий из taxonomy `0.3.0-spike`.
- Choice и Noul оценки, исходный статус Jev, отдельные сигналы `unlisted` и `insufficient evidence`, а также причины локального review по порогам.
- Сравнение с черновыми gold-метками, фильтры и сортировка, общая статистика и режимы A–E.
- Переключатель **Legacy / Policy v2.1**. Policy v2.1 показывает `positive / negative / abstain` отдельно для каждой категории; все сохранённые оценки и тема Choice остаются неизменными.
- В v2 событие с оценкой `≥ 0.80` становится **кандидатом, не фактом**. Если есть кандидаты и `insufficient evidence ≥ 0.80`, кандидаты удерживаются для проверки. Если кандидатов нет, высокий evidence сам по себе задачу не создаёт.
- `unlisted event ≥ 0.80` создаёт отдельную задачу проверки и не блокирует известные event-кандидаты. Низкий Choice и event `abstain` сохраняются, но сами по себе не отправляют новость на review.
- Экран сравнения старых правил и Policy v2.1 считает **локальные расчётные результаты** на одинаковом наборе из 45 ответов. Legacy показывает, какие целые новости прошли бы строгую проверку; Policy v2.1 показывает список event-кандидатов. Ничего не передаётся в T09/runtime. В таблице показаны совпадения и расхождения относительно предварительных меток.
- На экране статистики распределение кандидатов, лишних/пропущенных событий и причин проверки следует выбранному режиму. В Legacy оценки Noul сначала сравниваются с порогами, а затем общая проверка может удержать всю новость. В Policy v2.1 список кандидатов и отдельные задачи проверки только симулируются локально. График автоматического принятия и пресеты A–E остаются диагностикой старых правил. Предложенные пользователем метки меняют график расхождений локально и не заменяют исходную разметку.
- Локальная ручная корректировка меток. Она не меняет исходный корпус; предложения можно выгрузить в JSON со статусом `user_proposal_not_approved_gold`.
- Скриншоты разборного экрана и статистики находятся в `screenshots/`.
- Для Policy v2.1 добавлены снимки разбора, сравнения политик и мобильного экрана в `screenshots/policy-v2-*.png`.
- На узком экране сверка с предварительными метками стоит сразу после списка новостей, до длинного разбора всех оценок. Поля ввода используют размер текста 16 px, а основные кнопки — увеличенную область нажатия.

Встроенные оценки получены в сохранённом эксперименте. Перетаскивание порогов пересчитывает только интерпретацию этих оценок в браузере — модель повторно не запускается. Оценки не являются калиброванными вероятностями, а метрики на синтетическом корпусе и предварительной разметке не доказывают качество на реальных новостях.

## Актуальная Policy v2.1

Сводные результаты автоматически создаются в `policy-v2-results.json`; расчёт находится в `policy_v2.py`, Legacy и основной runtime не меняются. На тех же закреплённых ответах Legacy расчётно принимает целиком 3 из 45 историй и удерживает 42 на общей проверке. Policy v2.1 локально формирует 40 event-кандидатов в 32 историях; 34 кандидата совпали с предварительной разметкой, 6 — нет, ещё 7 ожидаемых меток отсутствуют в расчётном списке. Эти результаты не отправляются в T09 или runtime. На заданных порогах `0.80` ни один сигнал не создал review-задачу в симуляции: 43 event-оценки `abstain` просто сохранены, а высокий evidence без event-кандидатов нечего удерживать.

По предварительным меткам candidate-метрики: Precision 85.0%, Recall 82.9%, F1 84.0%, точный набор событий 34/45. Условная исследовательская группа «значимых» FP содержит 3 случая, против 0 у прошедшего Legacy-фильтр потока; эта группа не является утверждённой risk policy. Меньшее число задач в симуляции не доказывает безопасного снижения человеческой проверки: метки предварительные, а кандидаты не подтверждают факты. T09–T13 здесь только возможные будущие потребители; runtime-интеграции нет.

Предыдущая версия v2.0 сохранена в `policy-v2-results-2.0.0.json`; её результаты и тесты не переписываются. Полная история и актуальная проверка находятся в конце `TEST_REPORT.md`. Новых запросов к Jev не было.

## Обновить HTML из исходных файлов

Из корня репозитория выполните:

```powershell
python spike/T08/visualization/build.py
```

Генератор проверяет закреплённые SHA-256 корпуса, taxonomy и live aggregate; повторно запускает проверку воспроизводимости через существующий `quality_analysis.py`; затем встраивает минимальную проекцию данных, CSS и JavaScript в один файл. Если источники не совпадают с закреплёнными данными или перестают воспроизводиться исторические метрики, сборка завершится ошибкой.

## Проверить

```powershell
python -m unittest discover -s spike/T08 -p 'test*.py' -v
python -m unittest spike.T08.visualization.test_policy_v2 spike.T08.visualization.test_visualization -v
python -m ruff check spike/T08/visualization/build.py spike/T08/visualization/policy_v2.py spike/T08/visualization/test_policy_v2.py spike/T08/visualization/test_visualization.py
python -m ruff format --check spike/T08/visualization/build.py spike/T08/visualization/policy_v2.py spike/T08/visualization/test_policy_v2.py spike/T08/visualization/test_visualization.py
```

Тесты T08 и visualization запускаются отдельными командами: первая проверяет остальные модули spike, вторая — v2 и браузерный интерфейс. Они проверяют исходные hashes и количество ответов, Legacy baseline, A–E, v2 routing и метрики, локальные фильтры/пороги/экспорт, безопасность вывода, отсутствие внешних запросов и адаптивность. Для браузерного теста нужны Python-пакет Playwright и установленный Chrome; для ручного открытия страницы они не требуются.

Браузерные тесты сохраняют скриншоты во временную системную папку и удаляют её после проверки. Они не перезаписывают файлы в `screenshots/`.
