# T12 limitations and compatibility gaps

## Framework contract gaps requiring owner review

1. **Exact source reference materialization for Graph.build.** The Graph.build operation card (#14 in `docs/specs/framework-v1/03-operations.md`) accepts `BuildGraphInput.knowledge` with inline Statements and slices. The normative pointers `#/components/schemas/BuildGraphInput/properties/knowledge`, `#/components/schemas/KnowledgeSnapshot/properties/statements`, and `#/components/schemas/KnowledgeSnapshot/properties/slices` contain no aggregate `ObjectRef` values. Yet `GraphEdge.statement_refs` (`#/components/schemas/GraphEdge/properties/statement_refs`) needs a `StatementRef`, whose `aggregate_ref` and content `hash` are required (`#/components/schemas/StatementRef/properties/aggregate_ref` and `/properties/hash`; see `docs/specs/framework-v1/02-contracts.md`, “StatementRef.hash relates to the canonical Statement”). KnowledgeSlice supplies owner/partition/revision but not the aggregate content hash. The spike therefore takes exact `statement_ref_index` and `aggregate_refs` as additional explicitly materialized source inputs. A direct edge is omitted with `MissingDatum(unavailable)` if a ref is missing; no ref/hash is fabricated. This is a local experimental interface only, not a DTO change.

2. **Graph.publish materialized reads.** The Graph.publish card (#15) requires checking candidate references against source-owner versions. `PublishGraphInput` contains candidate and expected revision, not the materialized Business/Events source read outputs. `IsolatedGraphStore.publish` therefore requires an explicit `source_statement_refs` argument and fails closed if it is missing or does not match. This is local simulator input, not a contract extension or a hidden read.

3. **Negative assertion representation.** The normative GraphEdge DTO has no polarity field (`#/components/schemas/GraphEdge/properties`). A negative Statement such as `does_not_source_from_country` cannot safely be represented as a positive edge. The prototype preserves it as a `PreservedStatement` sidecar and adds an unsupported `MissingDatum`; it is not publishable as an ordinary relation. A contract owner must decide how negative knowledge should be represented before integration.

4. **Valid-time representation.** GraphEdge has no statement valid-from/valid-to fields. The manifest records one projection TimeSlice, and `TemporalEdgeContext` carries the source statement's exact valid and recorded time in the T12 sidecar. Historical data require rebuilding a graph at the requested cut; the normative graph-query DTO alone cannot perform per-edge temporal filtering.

5. **Manifest slice completeness and exact lineage boundary.** At publish, every `StatementRef` carried by node/edge grounding or provenance must match an explicitly supplied source ref and its aggregate must be represented by a slice in the candidate manifest. At query time, local `(statement_id, revision)` identity is qualified by aggregate owner, object ID and aggregate revision. References from distinct aggregates therefore do not conflict solely because their local IDs match. For the same aggregate-qualified identity, full refs must agree, including aggregate and statement hashes; conflicting refs are quarantined. Each edge ref must also map by aggregate owner, partition ID and revision to exactly one manifest `KnowledgeSlice`; a missing, conflicting, zero-match or multiple-match lineage edge is quarantined before traversal and never returned under any freshness policy. If such an edge borders the selected result, the response reports `MissingDatum(not_observed)` and freshness is `unknown`; `current_required` rejects it. The `StatementRef.aggregate_ref` has a hash, while `KnowledgeSlice` has neither that hash nor a field referenced by `StatementRef` for `selection_key`. Thus query can establish an unambiguous slice by owner/partition/revision, but cannot independently compare the aggregate hash with current owner data; it only detects inconsistent hashes among refs in the same aggregate-qualified identity. Exact source refs are validated at the isolated publish seam; this remaining read-time limitation is not a DTO extension. The store cannot prove that a manifest omitted an unrelated, unreferenced input slice without an independent expected-slice set.

6. **Scoped query boundary.** Graph.query operation card #16 (`docs/specs/framework-v1/03-operations.md`) says unrelated company partitions do not affect a scoped result. Query content follows `seed_ids`, relation filters, depth and node bounds; `required_slices` is a freshness input and does not filter edges or projected provenance. The graph manifest and selected-node/edge StatementRefs identify materialized graph dependencies. Business/Events source refs that identify those materialized partitions are also checked. Generic `Provenance.source_refs` and `evidence_refs` are context-specific pointers per `docs/specs/framework-v1/02-contracts.md` §Provenance; Graph.query does not resolve raw source/evidence artifacts as hidden current inputs. Thus Documents/Evidence refs remain intact without being treated as additional graph slices. A valid selected edge outside `required_slices` remains visible with complete provenance but makes freshness `unknown` and appears in `missing_slices`; `current_required` rejects it. A materialized StatementRef/Business/Events source ref without a matching manifest slice also makes freshness `unknown`, while remaining intact in the result. A changed declared current revision is `stale`; a missing, empty or unresolvable declared scope is `unknown`. An invalid-lineage edge makes freshness `unknown` only if it borders the selected nodes and passes the relation filter; otherwise it is quarantined from traversal but does not affect this query. With no seed, selection remains bounded by `max_nodes`; it does not implicitly require every manifest slice unless selected graph items use them or the caller declares them. Query scope does not establish completeness of unreferenced knowledge or hidden dependencies.

## Algorithm and evidence limitations

- Entity resolution is deliberately strict: supplied entity IDs remain distinct; there is no fuzzy resolver and no alias registry in this spike. A future alias may be used only after explicit review/materialization. Similar names, products, countries or industries never create an edge.
- Only a versioned predicate allowlist and one narrow company → supplier → supplier-location derivation are implemented. The inferred edge stays `inferred`, carries a method and exact input StatementRefs, and does not assert a confirmed source fact. No general multi-tier inference, probabilistic model, or model adapter is evaluated.
- The algorithm carries upstream `epistemic_status` and provenance. It does not validate the truth of upstream claims, establish Evidence owner records, or decide a trusted-owner policy. An exact source hash or verified anchor is not proof that the assertion is true.
- Disproved statements remain preserved in the build sidecar and cannot become positive edges. Query also skips/discards any `disproved` edge present in a manually constructed or imported snapshot. The GraphEdge DTO still has no polarity field, so explicit negative assertions remain sidecar-only.
- Published graph revisions and receipts are held in process-local mutable Python models, but the store returns deep copies on read, idempotency recovery and publish response; tested caller-side mutations do not alter stored history. This is an isolated simulator guarantee, not a persistence immutability or transaction guarantee.
- Edge IDs are stable hashes over the statement ID, statement revision and exact source StatementRefs, preventing revisions of one statement from colliding. The current `Graph.build` `KnowledgeSnapshot` adapter still indexes statements by `(statement_id, revision)` and rejects duplicate pairs. Query now resolves aggregate-scoped StatementRef identities correctly once they are present in a graph snapshot, but the build adapter cannot currently construct duplicate local IDs from separate aggregates; preserve fail-closed behavior there until an aggregate-qualified normative input mapping exists.
- The prototype reports a missing edge as unknown and leaves contradictory source values separate. It does not adjudicate which conflicting source is correct or calculate graph completeness/coverage.
- The BFS query is bounded and deterministic, but is a neighborhood query rather than a path-ranking, risk-scoring, or explanation algorithm. A no-path response is scoped to that supplied projection, slice, relation filter and bounds.
- Publish simulation is in-memory, process-local and intentionally small. It is not concurrency-safe persistence, transaction management, authorization, source-owner verification, or production Graph DB behavior.
- Shared data are synthetic and provisional. Expected properties are not independently approved gold labels; observed pass counts measure engineering behavior against those expectations, not real-world graph accuracy.
- No live model, vendor product, API, dataset, or external service was used. Model quality is NOT MEASURED. Vendor-reported coverage and performance are not independently verified; see `RESEARCH.md`.

## Integration status

**NOT READY.** Do not connect this prototype to Framework production operations until owners resolve the reference materialization and DTO gaps, decide alias/negative/time semantics, review trust-policy boundaries, and independently approve the test expectations. No production state or API is changed by this spike.
